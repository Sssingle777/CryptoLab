# CryptoLab 设计（0.3.0）

Python >=3.11，SDK 运行时仅标准库。以普通上下文管理器、SQLite 和本机文件系统实现，不引入 ORM、外部服务、队列或任务调度器。第三阶段的 Streamlit 是可选界面；页面调用管理函数，管理函数复用原有 Database 连接、事务及有限重试机制。

## 模块与公共接口

| 模块 | 职责 |
| --- | --- |
| `api.py` | `track_run`、`track_batch`、`update_run` 的公开签名。 |
| `recorder.py` | Run/Batch 生命周期、独立实例状态、计时、异常优先级和资源清理。 |
| `database.py` | schema、独立连接、短事务与有限重试、JSON 合并、心跳写入、修订审计。 |
| `heartbeat.py` | 每个活跃 Run 的低频守护线程，退出时停止并等待结束。 |
| `monitoring.py` | `get_run_status`、`get_batch_summary`；只读的活跃状态推导。 |
| `logging_utils.py` | 专用 logger、实时 Python 标准流捕获与捕获互斥检查。 |
| `artifacts.py` | 安全路径、无覆盖复制、附件登记、分块 SHA-256、目录描述符限定的安全读取。 |
| `records.py` | 手动 Run、软删除/恢复、异常结束确认、项目/方案管理、组合筛选和详情快照；不持有连接。 |
| `files.py` | 只读未登记文件扫描、人工附件登记审计、日志限量预览/搜索、安全下载。 |
| `presentation.py` | 标准库时区转换、日期边界与 CSV/JSON 导出。 |
| `web/app.py`、`web/views/` | 原生 Streamlit 导航与四页表单；不直接写 SQL，不调用实验或求解器。 |
| `adapters/gurobi.py` | 安全读取可选模型属性，不接触环境、参数或求解流程。 |

现有记录接口保持兼容；`track_run` 只增加可选 `heartbeat_interval_s=30`。查询和人工修订是独立函数，不要求用户改变已有实验的 `with` 写法。

## 为什么重构数据库写入

第一阶段已按操作创建连接，但仅设置 busy timeout，没有完整事务重试。若只重试事务中的单条 SQL，会存在旧读快照、重复写入或不完整审计的风险。因此第二阶段将数据库写操作交给 `_write`：

1. 在调用线程创建新连接，设置外键及 busy timeout。
2. 在读取将要修改的共享数据之前执行 `BEGIN IMMEDIATE`。
3. 运行一个只包含数据库操作的小函数，并提交。
4. 失败时回滚和关闭连接。仅 `SQLITE_BUSY` / `SQLITE_LOCKED`（包含扩展码）可有限重试；下一次重新开始整个事务。

默认 5 秒 busy timeout，最多 3 次额外重试，退避为 50/100/200 毫秒加 0–50 毫秒随机延迟。构造内部 `Database` 时可配置 `busy_timeout_ms`、`max_retries`，便于测试和本地维护；SDK 不引入全局连接池。磁盘错误、约束失败和 SQL 错误不重试。相关分类依据 [SQLite 错误码说明](https://www.sqlite.org/rescode.html)。

文件复制、散列、日志写入和用户计算位于事务之外，绝不随数据库重试重放。`connect()` 是低层连接上下文，不自动重跑调用者的任意代码；SDK 内部数据库操作使用 `_write` / `read` 管理重试。

读取使用短读事务，批次状态和子 Run 计数来自同一个快照；汇总逐行计数，不加载完整日志。WAL 允许普通读取与写入并行，写操作仍由 SQLite 串行执行。

## 运行、进程与线程边界

每次 Run/Batch 生成新 UUID；项目和方案按名称复用。Run 创建时保存批次公共参数与单次参数合并后的完整快照。每个 Run 有独立目录、专用 logger、错误状态和实例锁；实例锁只保护该 Run 的记录操作与退出清理，不串行化其他实验。

每个进程/线程按需打开自己的 SQLite 连接，保留默认 `check_same_thread` 检查。Database 只持有路径和配置，心跳线程可以使用同一 Database 实例来创建它自己的连接。Run、Batch、Database 不可 pickle，并对所属 PID 作检查；进程间传递 Batch ID 字符串。SQLite 连接和 Gurobi 模型不由 SDK 传递。

spawn 示例的 worker 放在模块顶层，进程池在 `if __name__ == '__main__'` 内创建，遵循 [Python multiprocessing 的 spawn 要求](https://docs.python.org/3.11/library/multiprocessing.html)。若 fork 子进程继承活跃 Run，捕获注册表会明确拒绝新建 Run，避免获取父进程遗留锁或使用其日志资源。不要在活跃 Run/后台线程存在时使用 fork。

`run.log()` 使用不向 root 传播的独立 Logger 和文件 Handler，每次输出及时 flush，不在内存积累日志。同一进程多个活跃 Run 不使用全局标准流代理。单 Run 显式开启 `capture_console=True` 时才代理 stdout/stderr；有重叠 Run 则拒绝捕获。原生求解器日志由调用者将 `LogFile` 设为自己的 `run.output_path`。

## 心跳与退出语义

创建 Run 时记录初始心跳，默认每 30 秒仅刷新 `last_heartbeat_at`。`updated_at` 表示最近的数据修改（参数、结果、状态、附件登记或人工修订），不随心跳和每行日志更新。旧版被心跳推进过的更新时间无法恢复，升级不批量修补历史值。心跳线程只写数据库，不触碰模型、附件或用户状态；它自己的单次写等待为 250 毫秒，无额外重试。失败时保留旧时间并在后续周期重试，连续失败报告一次；成功后重新允许报告新故障。心跳是尽力而为，不将故障转换成 Python 实验失败。

退出时在单调时钟上确定实验耗时，然后停止心跳并等待其线程结束，恢复标准流、关闭日志、登记存在的输出文件、冻结 raw 参数/结果、保存最终状态。异常收尾仍保存部分结果；若记录器同时出错，实验原始异常优先。未发生实验异常而记录失败时，SDK 报错，能写回状态时记录为失败，不伪造成功。

`process_id` / `thread_id` 指向进入 Run 的实验线程，不是心跳线程。时间存储为带时区的 UTC ISO 8601。`duration_s` 不等同于 Gurobi 的 `solver_runtime_s`。

## 状态待确认与批次统计

数据库只保存 `RUNNING / COMPLETED / FAILED / INTERRUPTED`。`get_run_status` 额外返回只读的 `display_status`：运行中且超过 `heartbeat_timeout_s`（默认 120 秒）时为 `UNCONFIRMED`；已结束记录直接显示其原状态。旧版没有心跳的记录回退到开始/创建时间。

超时不改数据库，不伪造结束时间，不判断进程死亡。原生计算长时间持有 GIL、系统休眠、时钟调整或数据库竞争都可能延迟心跳。心跳恢复后查询自动恢复显示 RUNNING。

Batch 状态继续表示父作用域退出结果；统计接口另行返回 total、completed、failed、interrupted、running、unconfirmed，五类计数互斥。一个子 Run 的失败不会回滚其他子 Run，父作用域结束也不会覆盖它们的状态。父进程应自行等待 worker；SDK 不负责调度。

强制终止时，已提交记录和已经写入的文件保留，重新打开数据库不会清理。未执行退出登记的日志/输出可能暂时没有附件元数据。第三阶段增加显式人工确认和文件补录；不会自动继续求解、补写结果或把待确认记录判为失败。

## 修订审计与历史兼容

六张表和索引沿用 schema v1，不需要迁移，不删除旧表。`user_version` 比 SDK 更新时拒绝使用。原始需求文件保持不变。

`update_run` 只接受未删除、已结束记录的 params、metrics、notes、开始/结束时间、耗时和 solver 字段；不允许修改状态或 raw 快照。必须提供原因，actor 固定 local_user。JSON 参数/指标为完整替换；保存旧值、新值和原因的审计行与实际更新处于同一短写事务。审计失败全部回滚；并发修订会读取前一次提交后的值，形成连续审计链。相同内容不新增审计，JSON 布尔值与数字区分。可选 `expected_updated_at` 支持旧页面冲突检测，旧 API 不传该参数仍按原行为工作。

手工时间规范化为 UTC。改变开始/结束时间且未显式给出耗时时，根据已知时间重算；不完整时间保留空耗时，所派生的耗时变化也进入审计。活跃及待确认 Run 禁止手工编辑，避免覆盖仍可能继续写入的实验。

## 第三阶段的最小扩展

没有更换数据库核心、日志或并发模型，也没有改 schema。必要调整只有：抽取已有项目/方案/Batch 参数解析供手动录入复用；抽取审计和 UTC 规范化函数；增加 Run 修订的可选版本校验及 solver 字段；修正心跳与附件登记的 `updated_at` 语义。管理功能按业务放入 `records.py`、`files.py`，避免将页面 SQL 或大量管理逻辑塞入记录器。

```text
src/cryptolab/
  api.py, recorder.py, database.py, heartbeat.py, monitoring.py  # 原有记录核心
  records.py          # 管理数据与生命周期
  artifacts.py        # 原有附件处理与安全打开文件
  files.py            # 管理附件与日志读取
  presentation.py     # 时区和导出（不依赖 Streamlit）
web/
  app.py              # 导航、回环地址检查、时区
  common.py           # 共享表单和展示
  views/
    runs.py           # 筛选、可选定期刷新、导出
    projects.py       # 项目/方案管理、Run 与批次汇总
    details.py        # 详情、修订、审计、文件、删除与确认
    manual.py         # 历史实验录入
.streamlit/config.toml
```

手动记录与 SDK 使用同一 runs 表和 UUID 目录，source 为 manual。开始/结束/耗时缺失则为空，不生成 PID、心跳或自动 raw 快照。首次创建写审计，已结束记录修订保留自动 raw 快照。软删除仅设置 deleted_at 并审计，恢复清除该值；附件和其他实验均保留。原有批次统计已排除软删除记录，继续沿用。

人工结束必须同时满足：原状态 RUNNING、心跳超时、用户明确核实进程停止、保存时 heartbeat 与 updated_at 仍匹配读取值。同机已知 PID 必须经信号 0 探测确认不存在；仍存活或无法判断均拒绝。确认仅能写 INTERRUPTED/FAILED，未知结束时间仍为空。原始自动快照仅从最后已提交值冻结，确认依据/状态/时间变化同事务审计。任何审计失败回滚所有数据库更改。PID 复用采取保守拒绝，主机或 PID 缺失依赖人工判断，不用心跳超时替代死亡证据。

文件扫描不更新数据库，不自动登记，也不创建缺失 Run 目录。候选文件分块散列；补录重新散列并与扫描结果比较，事务内安全重开文件检查 inode/大小/纳秒修改时间等身份信息，再写附件元数据与审计。大文件复制、散列都在写事务外。原子性限于数据库元数据与审计；上传文件已复制但数据库失败时保留未登记文件供再次检查。只补录已结束且未删除 Run，临时文件、符号链接、硬链接和非普通文件拒绝。读取使用目录描述符与 no-follow，避免路径替换使预览/下载越过 Run 目录。该实现依赖 macOS/Linux 文件 API，未验证 Windows。

日志默认只读末尾 256 KiB / 300 行；搜索按最多 64 KiB 字符片段读取，保留跨片段匹配，默认至多 200 段结果。下载需用户点击准备，随后 Streamlit 持有完整下载数据；大文件会占内存，SDK 写日志仍逐条流式落盘。没有附件执行或任意文件路径读取界面。

界面时间默认 Asia/Shanghai，可选 IANA 时区；UTC 原值同时可见。没有时区的表单时间按所选时区解释，拒绝无法确定的夏令时边界。筛选的日期结束日包含全天，转成 UTC 半开区间查询。CSV/JSON 保留 UTC；JSON 保留类型，CSV 保护公式前缀并将 params/metrics 编码为 JSON 单元格。列表/导出暂为整批加载，适合个人本机使用。

页面无独立 SQL、连接池、缓存副本或调度线程。列表开启自动刷新时由 Streamlit fragment 每 5 秒重新查询，详情表单不会定时刷新覆盖未保存编辑。UI 和 SDK 可共用同一数据库，但一个页面操作的数据库锁只覆盖其自身短事务。

## 验证方法与边界

第一阶段原有 70 项测试保留。心跳由第一阶段的空字段改为实际写入，所以只将其中一个“心跳为空”断言更新为检查有效初始心跳。其他原有行为继续回归验证。

第二阶段测试实际启动独立 Python 子进程、spawn 进程池及线程池；验证 40/60 条 Run，以及需求文档的 4 个 worker 各 20 条 Run。检查数量、UUID、参数和结果、日志内容、附件大小/散列、真实 PID/线程 ID，并在写入期间运行状态查询。

可靠性测试使用真实 SQLite 写锁，覆盖竞争成功、有限重试耗尽、事务回滚及错误分类；使用真实强制终止验证部分记录保留和待确认状态。心跳单测用较短可配置周期观察多次更新，并检查停止、故障提示与恢复。审计测试覆盖并发修订、原始快照冻结及触发器故意拒绝审计后的整体回滚。

第三阶段另有后端测试和 Streamlit AppTest，覆盖页面交互、校验、编辑冲突、文件补录及并发查询。实际 Gurobi 环境/许可证并发求解不在本机验收范围；自动测试使用假模型。强制进程终止测试不代表真实断电/文件系统故障验证。
